## 2. 第一阶段实际基线

### 2.1 架构与模块

- 后端是 Python 3.9+、FastAPI、PyMongo 的模块化单体；`backend/app/main.py` 组装应用、会话中间件、来源校验、路由和静态资源，并在 MongoDB lifespan 中初始化索引。
- `accounts`、`questionnaires`、`responses`、`statistics` 按 API/Routes、Service、Repository 分层；条件跳转和答案校验在 `responses/engine.py`，不是路由内联逻辑。
- 前端为由 FastAPI 同源托管的原生 HTML/CSS/JavaScript 单页，没有独立前端框架或构建步骤。主要管理、填写和统计交互集中于 `frontend/js/app.js`。
- 业务持久化使用 MongoDB；没有关系数据库，也没有现成问卷框架。当前没有独立题库、题目版本、分享授权或迁移模块。

### 2.2 集合、关系与索引

| 集合 | 当前实际内容与关系 | 当前启动索引 |
|---|---|---|
| `users` | 账号、规范化用户名、Argon2id 密码哈希及时间戳 | `username_normalized` 唯一索引 |
| `surveys` | 创建者、标题、匿名/重复提交策略、状态、截止时间，以及嵌入式 `questions[]`；题目内嵌选项、校验、跳转规则 | `(owner_id, updated_at desc)` |
| `responses` | `survey_id`、`respondent_id`、draft/submitted 状态、`revision`、`lifecycle_guard`、嵌入式 `steps[]` | `(survey_id, respondent_id, lifecycle_guard)` 部分唯一；`(survey_id, status, submitted_at desc)` |

题目 ID 和选项 ID 是字符串；集合文档 ID 是 `ObjectId`。题目数组顺序就是问卷顺序。`responses.steps[]` 只记录实际经过题目，包含 `answered` 或 `skipped`；修改前序答案时，服务端重算路径并清除失效步骤。

### 2.3 核心业务流程与 API

- 账号：`/api/auth/register|login|logout|me`。登录后用签名 Cookie 保存用户 ID；创建者查询以 `owner_id` 限权。
- 问卷：`/api/surveys` 创建/列表，`/{id}` 详情与元数据更新，`/{id}/questions` 添加/改/删草稿题目，`/{id}/publish` 发布，`/{id}/close` 关闭，`/{id}/deadline` 管理截止时间。状态为 `draft → published → closed`；发布后题目及填写策略锁定。
- 填写：`/api/fill/{survey_id}` 读取分享问卷；`/responses` 创建或恢复草稿；`/steps/{question_id}` 逐题保存；`/submit` 校验完整路径后提交。匿名问卷仍要求登录，但创建者视图不返回填写者身份。
- 统计：`/api/statistics/surveys/{survey_id}` 和 `.../questions/{question_id}` 仅问卷创建者可读。当前只统计该问卷中 submitted 答卷的 answered 步骤。
- 核心题型为单选、多选、文本、数字；服务端执行选项归属、数量、长度、数值范围、整数、必答和跳转目标校验。跳转规则允许向后跳转，支持单选、多选 ANY/ALL 和数字比较。

### 2.4 测试基线与边界

当前 `tests/` 包含健康检查、注册、会话、问卷、答卷/跳转和统计测试。使用 `.venv/bin/python -m pytest -q` 的本轮实际结果为 **12 passed、29 skipped**；29 项是需要 `MONGODB_TEST_URI` 的 MongoDB 集成测试，本轮没有配置可运行集成测试的数据库，所以不能将它们记作通过。直接执行 `.venv/bin/pytest -q` 在本 shell 中因 `ModuleNotFoundError: backend` 失败；改用模块入口才完成上述测试收集与执行。

## 4. 推荐版本化与题库设计

### 4.1 建议的数据结构

| 集合/字段 | 建议内容与用途 |
|---|---|
| `question_families` | `_id`、`owner_id`、创建时间、归档状态、可选的默认推荐版本 ID。代表可共享/分叉的逻辑题目身份，不把“同文案”自动当作同一题。 |
| `question_versions` | `_id`、`family_id`、族内 `version_no`、`parent_version_id`、可选 `restored_from_version_id` 或跨族 `derived_from`、不可变题干/题型/选项/校验快照、`content_hash`、创建者与时间。每个版本新增一份文档。 |
| `question_shares` | `family_id`、`recipient_user_id`、权限、分享者和时间。首版只做用户级授权；系统当前没有团队实体。 |
| `question_banks` | `_id`、所有者、名称、可见性和时间。题库可为个人库；团队题库需等团队/组织权限模型确认后再扩展。 |
| `question_bank_items` | `bank_id`、`family_id`、所选 `version_id`、加入者和时间。条目选用哪个版本是显式的，不随题目族的默认版本静默变更。 |
| `surveys.questions[]` | 保留当前完整嵌入定义；题目增加可选 `library_ref: {family_id, version_id}`。`question_id` 仍是问卷内 ID，跳转目标仍使用问卷内 ID。 |
| `responses` | 不改变既有字段和 `steps[]` 结构。答卷仍由 `survey_id` 和嵌入题目 `question_id` 解释。 |

版本快照记录可复用题目内容（题干、题型、必答、选项、校验）。现有 `jump_rules.target_question_id` 指向问卷内另一题，无法在不同问卷直接复用；建议题库版本默认不保存可执行跳转目标，插入问卷时清空 `jump_rules`，由问卷作者按目标问卷重新配置。若未来需要保存跳转模板，必须设计目标题映射，不能复制旧目标 ID 后假定有效。

题目版本是追加式：普通编辑从指定父版本创建新版本；历史版本不可原位更新。恢复旧版本时以当前版本为父，复制旧版本内容生成新版本，并记录 `restored_from_version_id`。分叉也新增版本，可从非默认版本创建。版本号在同一题目族内递增，但父子字段表达实际分支关系。

### 4.2 使用追踪与统计定义

题目快照的 `library_ref` 是使用关系的主来源；按族或版本查询 `surveys.questions.library_ref.*`，再返回具体问卷和问卷内 `question_id`。这避免同时维护 `surveys` 与 `question_usages` 两份可失配数据。查询须按授权过滤问卷元数据；共享题目使用者默认只能看到自己问卷的使用记录，题目族所有者看到哪些他人问卷使用了题目需要单独授权规则。

跨问卷统计建议以“题目族 + 精确版本”为默认统计单元。相同题目族内不同版本分开展示；若用户选择合并，只有题型、选项语义和校验口径兼容的版本才可明确合并，不能仅凭同一题目族自动合并。查询将匹配题目族/版本的 survey 快照引用，逐问卷定位 `question_id`，只纳入 `responses.status == submitted` 且步骤 `status == answered` 的答案；保留现有单问卷统计路由及返回格式。

### 4.3 MongoDB 索引与理由

| 集合 | 建议索引 | 理由 / 注意事项 |
|---|---|---|
| `question_families` | `{owner_id: 1, updated_at: -1}` | 列出个人题目库和最近修改项。 |
| `question_versions` | 唯一 `{family_id: 1, version_no: 1}`；另建 `{family_id: 1, created_at: -1}`、`{parent_version_id: 1}` | 保证族内版本号唯一、按族读取历史和查找分支。 |
| `question_shares` | 唯一 `{family_id: 1, recipient_user_id: 1}`；另建 `{recipient_user_id: 1, family_id: 1}` | 防止重复授权并快速列出收到的共享题目。权限仍需 Service 校验。 |
| `question_banks` | `{owner_id: 1, updated_at: -1}` | 列出本人题库。 |
| `question_bank_items` | 唯一 `{bank_id: 1, family_id: 1}`；另建 `{family_id: 1, bank_id: 1}` | 同一题目族在同一本库中不重复，并支持反向查题库。 |
| `surveys` | 多键 `{questions.library_ref.family_id: 1, questions.library_ref.version_id: 1}` | 由嵌入快照查询使用位置；复用现有 owner/status 字段做可见性过滤。需用实际 MongoDB 版本验证复合多键索引和查询计划。 |
| `responses` | 先复用当前 `(survey_id, status, submitted_at)`；代表性数据 `explain()` 显示单题扫描成本高时评估 `{survey_id: 1, status: 1, steps.question_id: 1}` 多键索引 | 先保持写入成本低；跨问卷统计新聚合必须评估扫描和内存，不预设物化计数。 |
| `schema_migrations`（迁移记录） | 唯一 `{migration_key: 1}` | 支持迁移幂等、断点恢复和失败记录。 |

跨集合引用完整性没有 MongoDB 外键保障。`family_id`、`version_id`、授权对象和问卷快照引用的存在、归属、权限及内容哈希匹配均由 Service 校验。索引创建失败时不应让服务静默以无索引模式开放新接口。

## 5. 已发布内容不变与旧答卷兼容

1. 发布问卷时，`surveys.questions[]` 中完整题干、选项、校验和跳转规则继续作为发布快照。发布后不再允许题目编辑；修改题库版本只写新版本文档，不修改被引用的 survey 快照。
2. 填写服务当前从已发布问卷读取内嵌 `questions`，`responses.engine` 用该定义验证答案和计算路径；统计服务也用同一问卷定义解释旧答卷选项标签。第二阶段应保持这一读取链，不在答题或统计时动态加载“最新题目版本”。
3. 新建/加入题库题目时把明确版本复制进 draft 的 `questions[]`，生成该问卷自己的 `question_id`，写 `library_ref` 作为来源指针。问卷快照字段与源版本脱离后分别保存；改题只能明确选择“创建新版本”或“在此问卷分叉/脱离来源”。
4. 现有 `responses.steps[]` 无需批量添加新字段；旧数据仍以 `survey_id + question_id` 对应原问卷快照。现有题目 ID、选项 ID、答卷值、提交状态和统计语义不变。对于题目选项，版本编辑时只有语义相同的选项才保留 `option_id`；新增/改义选项应生成新 ID，避免误读旧值。
5. 关闭题库条目、撤销共享或归档题目族只影响未来浏览/选用；不得删除历史版本，也不得让已发布问卷引用失效。已发布问卷内容和已提交答卷继续可读、填写状态按第一阶段规则执行。

## 6. 迁移、旧接口兼容与失败安全

### 6.1 推荐迁移步骤

1. **先只读盘点**：统计 surveys/questions 数量、状态、缺失或重复 ID、现存 response 引用及 BSON 文档大小；备份并输出可复核清单。对相同题干不自动合并题目族，避免把语义相近题误判为同一身份。
2. **先加集合与索引**：创建版本、授权、题库和迁移记录集合及新索引；保留 `users/surveys/responses` 字段、既有索引和现有读取路径。新 API 在数据准备完成前保持不可用或由功能开关关闭。
3. **幂等回填**：推荐将每个已有问卷题目作为独立来源，生成一个题目族及 v1 版本，避免文本去重；写入稳定 migration key 和内容哈希。之后仅给原 `surveys.questions[]` 添加可选 `library_ref` 元数据，不改 `question_id`、题干、选项、验证、跳转或数组顺序。对每个问卷使用原题目数组/更新时间作 compare-and-set，遇到并发变更则跳过并重试，不覆盖新值。
4. **核对后开放**：比较迁移前后题目核心字段哈希、数量、响应引用和抽样旧问卷统计；检查每个 library_ref 都指向存在的不可变版本。未完成或校验不一致时关闭题库/跨问卷 API，新旧问卷 API 仍从既有快照服务。
5. **支持重试/回退**：迁移用 upsert/唯一迁移键和游标支持断点恢复；孤立版本可以保留并标为未引用，不能因回滚而级联删除已用版本。回退时关闭新路由/功能开关、保留新增集合；若去掉 survey 元数据，必须再次按内容哈希和 CAS 定位，只移除 `library_ref`，不能重写题目主体。

最终采用逐个旧题目实例建立身份/初始版本并加入题目所有者默认个人题库的方案；只有满足安全校验的题目会被关联，无法安全映射的保留原状并报告。共享授权没有随迁移生成。

### 6.2 API 与写入失败处理

- 保留所有现有 `/api/surveys`、`/api/fill`、`/api/statistics/surveys/...` 路径、权限、请求字段和状态码；旧问卷题目没有 `library_ref` 时按原逻辑处理。
- 新增独立题库/题目版本 API；旧的题目增删改接口仍只操作本人 draft。响应可增加可选来源字段，但不改变原字段含义；输入模型继续允许现有请求体。
- 现有 `surveys.questions[]` 与 `responses.steps[]` 是兼容锚点。新版本服务层可以新建 `question_bank`/`question_library` 模块，再由 `main.py` 注册路由和索引，不重写既有 modules。
- MongoDB 当前未使用跨集合事务。先插入不可变版本，再用 CAS 更新题目族默认版本/题库条目/草稿快照；后续步骤失败时保留可重试的未引用版本并返回冲突/服务错误，不删除或覆盖旧版本。所有步骤需幂等、记录错误并可重试。
- 发布与编辑仍通过状态/原字段 CAS；权限查询失败、引用缺失、版本哈希不匹配、索引未就绪时按失败关闭处理，不退回“自动取最新题目”。新聚合/迁移不得读取或返回密码、答题人 ID 等无关信息。

- **兼容与前端**：旧 API 原请求继续成功且权限/状态码不变；新功能在桌面和移动视口可使用；版本/共享失败有清晰提示，重试不产生重复版本。

## 8. 主要风险与设计取舍

1. **共享权限与隐私**：指定用户的精确版本授权、撤销和 Service 层权限校验已实现。分享只授予查看/复用对应不可变版本；使用清单按问卷所有权过滤，题目所有者对其他用户只看到版本级汇总。跨问卷答卷统计尚未实现，未来也不能从共享关系推导查看他人答卷的权利。
2. **版本统计口径**：默认按精确版本分别统计已确定。题干相同不代表量表/选项语义相同；如未来支持跨版本合并，需另行定义兼容规则并由用户显式选择。
3. **跳转规则复用**：规则目标是问卷本地题目 ID。最终规则已确定且已实施：复用只复制题目定义，清空原跳转，使用者在目标问卷重新配置。
4. **跨集合原子性**：题目族、版本、题库条目与 survey 快照跨集合写入，现系统没有事务。采用不可变版本、CAS、幂等迁移和保留孤儿版本可避免破坏旧数据，但要有冲突提示和修复/审计日志。
5. **数据量与查询成本**：跨问卷统计要定位多份问卷和答卷；当前统计逐条读取聚合步骤，项目未做大数据压力测试。先以 MongoDB 聚合、索引和 explain 验收；不预先引入物化统计，必要时另行设计刷新一致性。
6. **兼容快照与题库双重事实**：版本库是可复用源，survey 嵌入题目是实际问卷事实。不能让填写时实时跟随源版本，否则破坏发布内容和旧答案解释；使用追踪只记录来源，不替代问卷快照。
7. **遗留题目身份**：旧系统没有题目族 ID，无法可靠从文本推断同一逻辑题。最终规则已确定且迁移脚本按每个 `(survey_id, question_id)` 独立建族，不依据相同文字合并。

## 9. 已确认的最终设计决策

以下规则由用户在第二阶段实施指令中明确确认，不再作为待确认事项：

1. 题目默认私有；题目共享采用指定用户授权。获授权用户只能使用原题，不能直接修改所有者的题目版本。共享不赋予查看其他用户问卷、使用清单详情或统计结果的权限。
2. 第一阶段每个旧题目实例单独建立题目身份和初始版本，按 `(survey_id, question_id)` 映射，不按相同文字自动合并。
3. 已发布问卷保留原题目内容、问卷内题目 ID、跳转规则和历史回答。问卷内嵌快照仍是填写及单问卷统计的权威定义；新增来源题目/版本引用不改变旧数据语义。
4. 复用题目时生成新的问卷内题目 ID，复制题目内容和校验规则，保存来源题目族 ID 与版本 ID。跳转目标属于问卷，复用时清空来源跳转并由使用者重新配置。
5. 题目修改追加不可变版本；历史可查询；从旧版本恢复时创建新版本并记录被恢复版本，不覆盖历史文档。
6. 跨版本统计默认按精确版本分别计算。未来跨问卷统计只读取当前用户有权限访问的数据。
7. 共享授权与问卷可见范围、使用清单详情和统计权限分离；共享题目不附带上述额外权限。

原方案中关于分享是否可分叉、是否自动更新条目、统计是否跨版本合并等提问，按以上规则处理：分享只授予使用原题；题库条目版本必须显式更新；版本分开统计。团队共享、跨版本兼容合并等未纳入本批，后续若需支持应单独确定策略。

## 11. 当前主要风险与部署前事项

1. MongoDB 多集合操作不使用事务。插入版本后题库/问卷关联失败可能留下未引用但不可变的版本；重试应可识别并复用，不能删除已引用版本。
2. 第二批索引升级会拒绝在旧的题目族级共享索引下发现非空授权记录，要求先人工审查，不会扩大旧授权范围；部署前应确认既有数据状态。
3. 性能验证使用 500 份问卷、8,100 份答卷的隔离样本，并非高并发、千万级数据、故障切换或生产容量验证。真实数据库迁移仍未执行。
4. 跨问卷查询采用受索引约束的单条 MongoDB 聚合并流式处理结果；文本回答仍需随统计响应返回，数据量显著增长时应另行评估分页/导出和响应体上限，不应引入未验证的一致性缓存。

**建议后续顺序：**部署前在目标 MongoDB 版本和隔离副本上核对新增索引与迁移 dry-run 报告；按批准窗口显式执行数据迁移；再进行更大样本和并发负载测试。当前变更没有对真实数据库执行迁移。

## 12. 第二阶段第二批实际实施情况

### 12.1 共享授权、撤销与使用清单

- 复用现有 `question_shares` 集合，授权粒度为 `(family_id, version_id, recipient_user_id)`，权限为 `use`。授权记录包含所有者、接收者、状态、授权/撤销时间；重复授权和撤销幂等，重授权是明确的状态恢复。新版本不会继承授权。
- 题目所有者只能分享自己的真实版本给现存指定用户；接收者只能读取和复用 active 的精确版本。查看历史、创建/恢复版本、管理题库和授权仅限题目所有者。Service 校验所有 API 权限，非所有者/未授权资源按 404 隐藏。
- 复用继续将不可变题目内容复制进问卷，产生独立的本地题目 ID 和空跳转规则。撤销只修改授权状态，不删除问卷快照、不改变发布问卷、答卷或既有统计。接收者对复用后的草稿本地修改不会创建/修改原所有者的版本。
- 使用清单实时查询 `surveys.questions[].library_ref`，不新建冗余 usage 集合。问卷所有者可逐条查看自己的问卷使用；题目所有者只得到其他用户按来源版本分组的精确/本地修改数量，不返回问卷 ID、标题、所有者或本地题目 ID。接收者需要当前 active 的精确授权版本，只能看自己问卷明细，不得到他人汇总。
- `question_shares` 建立版本/接收者唯一索引、按接收者状态查询索引和按族版本授权状态索引。旧的题目族级预留索引若非空，启动失败关闭，避免将宽泛旧记录默认为所有版本授权。Schema 详情见 `docs/mongodb-schema-v1.1.md` 第 12 节。
