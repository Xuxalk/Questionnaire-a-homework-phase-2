## 使用边界与说明

### 本轮用户提示词（原文）

以下原文来自 2026-10-28 本轮用户消息；早期轮次若只能从现存记录还原任务摘要，仍按摘要标注，不补写不存在的逐字文本。

```text
第二阶段八项功能已实现，第三批基线为 62 passed、0 failed、0 skipped。现在停止功能扩展，进入最终质量审计、兼容性验证与交付准备。

继续使用原项目目录和 main 分支，不新建 stage2 目录，不重置已有修改，不操作真实业务数据库，也不要自动提交或推送 Git。

本轮任务：

一、代码与需求最终审查

对照老师原始需求变更中的八项要求，逐项核对真实实现、API、前端入口和自动化测试。

重点复查：

- 不可变版本及历史恢复。
- 已发布问卷的快照保护。
- 共享撤销及跨用户越权。
- 旧题目与新题目关联的兼容性。
- 同版本跨问卷统计的正确性。
- 草稿、跳过、重复提交和多题目实例的计数。
- 多集合操作失败后的数据一致性。

只修复确认存在的问题，不做无关重构。

二、迁移与兼容性演练

构造具有第一阶段原始 Schema 的非空测试数据库，包含已发布问卷、跳转规则、有效及跳过回答、历史统计数据。

在隔离数据库中执行：

1. 迁移前的数据与统计基线采集。
2. dry-run。
3. 显式 apply。
4. 重复 apply，验证幂等性。
5. 模拟中断或部分失败后重新执行。
6. 对比迁移前后的问卷内容、题目 ID、跳转规则、答卷和统计结果。

记录迁移前后集合数据量、迁移结果及异常处理过程。不得对真实业务数据库执行 apply。

三、测试完善

运行完整 pytest，修复能安全解决的 Pydantic warning。

若现有浏览器测试工具可用，为核心业务流程增加一条可重复运行的自动化冒烟测试；避免为了测试引入复杂的新架构。

保留之前的真实浏览器验收记录，明确区分自动化测试、手工浏览器验收和性能测试。

四、MongoDB 设计与性能审查

检查新增集合、字段、索引、唯一约束和实际查询计划。

重点解释：

- 为什么采用独立题目版本集合。
- 为什么问卷仍保留题目快照。
- 如何通过 library_ref 追踪题目来源。
- 为什么没有新增冗余使用记录及统计缓存。
- 当前跨问卷统计的性能、适用规模与限制。

五、整理第二阶段实验报告初稿

在现有 docs 目录创建 `phase2-project-report.md`，沿用第一阶段学术、直观、简约的报告风格。

报告应包含：

1. 项目目标与第一阶段架构概述。
2. 新需求及变更影响分析。
3. 数据库设计演化与 Schema 对比。
4. 核心业务实现：复用、版本、共享、题库和统计。
5. 旧功能兼容及迁移方案。
6. 测试、浏览器验收和性能结果。
7. AI 使用过程、人工设计决策与修正。
8. 问题、解决方法、局限和总结。

六、交付检查

检查 README、运行说明、依赖、配置示例、MongoDB 索引初始化、迁移说明、文档链接与 Git 状态。
```
