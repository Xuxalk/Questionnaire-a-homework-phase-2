# 基于 MongoDB 的在线问卷系统——第二阶段项目报告（初稿）

**报告状态：**初稿，等待审阅；**整理日期：**2026-10-28；**项目基础：**第一阶段原有工程；当前工作分支为 `main`

## 1. 项目目标与原有架构

第二阶段依据教师提供的需求变更，在第一阶段系统上增量扩展题目复用、题库、版本、共享、使用追踪和跨问卷统计。项目保留第一阶段的账号、问卷、填写、跳转、提交及统计模块，没有另建阶段目录或替换原工程。

原架构为 FastAPI、PyMongo 与 MongoDB 组成的模块化单体。后端按 `accounts`、`questionnaires`、`responses`、`statistics` 分模块并分离 Routes、Service、Repository；前端由 FastAPI 同源托管原生 HTML、CSS 和 JavaScript。问卷题目嵌在 `surveys`，答卷作为独立集合保存并嵌入答题步骤。第一阶段完整功能、跳转和答卷状态模型见[第一阶段报告](phase1-project-report.md)。

## 2. 新需求与设计演化

原有模型把题目定义保存在某份问卷中，无法安全维护一个可复用题目、保留修改历史或统计精确版本。第二阶段增加独立的题目身份和不可变版本，但仍保留每份问卷自己的题目快照：题库是来源与编辑历史，问卷快照继续是发布、填写、跳转、答卷解释和单问卷统计的事实来源。

| 教师新增要求 | 本阶段处理方式 |
|---|---|
| 保存常用题目并复用 | 提供个人题库；复用时固定选定版本，复制内容和校验，并生成新的问卷内题目 ID。 |
| 共享给指定用户 | 默认私有；所有者仅能授权给指定用户使用指定版本。接收者不能修改来源题或查看未授权版本。 |
| 修改不影响旧问卷 | 修改只追加新版本；发布问卷继续读取本地快照。共享撤销不回收已经复制的问卷快照。 |
| 查看历史并恢复 | 版本记录父版本；恢复旧内容时创建新版本并保存恢复来源，不覆盖历史文档。 |
| 多版本并存 | 版本可从历史父版本分叉；题库条目显式选择版本，问卷也固定自己的来源版本。 |
| 查看使用情况 | 从问卷快照的 `library_ref` 实时查询；按题目实例列出本人问卷，对其他用户的使用仅提供版本级汇总。 |
| 管理题库 | 支持个人默认题库、自定义题库、加题、移除题目及明确更新条目所选版本。 |
| 跨问卷统计 | 按题目族和精确版本查询当前用户有权访问的已发布/关闭问卷；提供分问卷与汇总视图。 |

完整决策、各模块影响与逐批实现状态见[需求变更影响分析](phase2-change-impact-analysis.md)。

## 3. 数据库设计演化

第一阶段 `users`、`surveys`、`responses` 集合保留。`responses` 不增加题目版本字段或改写旧步骤；迁移也不改动其中任何答卷。

| 新增集合/字段 | 用途及主要约束 |
|---|---|
| `question_families` | 表示题目身份和所有者；每个旧问卷题目实例独立建族，不按相同题干合并；保存最新版本指针。 |
| `question_versions` | 保存题干、题型、选项和校验的不可变版本快照；族内版本号唯一，并保存父版本、内容哈希和恢复来源。 |
| `question_banks`、`question_bank_items` | 保存用户题库和显式选定的题目族/版本；同一题目族在同一本库中唯一。 |
| `question_shares` | 以题目族、版本、接收者为授权粒度；默认无授权，撤销保留记录。 |
| `surveys.questions[].library_ref` | 可选的来源族和来源版本关联；不取代题干、题目 ID、校验或本地跳转快照。 |
| `schema_migrations` | 保存最后一次迁移报告，支持排查和重试。 |

版本独立存储，便于追加历史、按父版本分叉和授权精确版本；继续在问卷内保存快照，避免题库更新改变已发布问卷或历史答卷的解释。`library_ref` 用于回溯来源、列出当前使用位置和按具体版本统计。使用清单和统计均直接查询问卷快照，没有额外双写 usage 集合或计数缓存，避免两份使用事实或过期统计。字段、索引和查询理由详见[MongoDB Schema](mongodb-schema-v1.1.md)。

启动时由现有 Repository 初始化索引。关键新增约束包括族内版本号唯一、来源问卷/题目映射唯一、每名用户唯一默认题库、题库条目唯一及精确版本共享唯一；`surveys` 有来源族/版本多键索引和 owner+来源复合索引，`responses` 沿用问卷/状态/提交时间索引。

## 4. 核心业务实现

- **复用：**用户从自有或获准的精确版本选题。服务端复制题目内容及校验规则、生成新的本地题目 ID，并清空来源问卷的 `jump_rules`。跳转目标是问卷局部 ID，由使用者在新草稿里重新配置。
- **版本：**版本内容通过追加写入保存。编辑从指定父版本建立分支；版本历史可查看父子关系；恢复操作创建新版本并记录 `restored_from_version_id`。版本文档没有修改和删除接口。
- **共享：**所有权、当前授权和版本范围由 Service 验证。授权仅允许读取、复用指定版本，不授予修改、恢复、问卷、使用明细或答卷统计权限。新版本不继承旧版本授权；撤销不影响问卷快照。
- **使用追踪：**实时读取 `surveys.questions[].library_ref` 并区分题目族、版本、本地题目 ID 和问卷所有者。问卷所有者看到本人逐项信息；题目所有者对他人问卷只能看到版本级数量，不收到问卷 ID、标题或所有者标识。
- **跨问卷统计：**MongoDB 单条聚合先按当前用户、可统计问卷状态和精确 `library_ref` 定位实例，再通过本地题目 ID 关联提交答卷的 answered steps。按实例和有效提交回答计数；draft、skipped、未到达及答案结构不兼容的数据不进入汇总。共享不扩大问卷答卷可见范围。

API 及输入/错误约定见[API 文档](api.md)，本报告不重复列举完整接口参数。

## 5. 旧功能兼容与迁移

迁移为显式运行脚本，默认 dry-run；应用启动只建立索引，不自动回填。apply 为每个合法旧题建立私有题目族、初始版本和默认题库条目，然后只给原题增加 `library_ref`。相同文案不合并；重复执行使用来源唯一键、内容哈希及问卷题目匹配更新。旧题无法安全验证时保持原状并记录原因，不删除旧数据。

2026-10-28 在独立 MongoDB 8.3.11 测试实例做了端到端迁移演练。旧 Schema 样本为 1 用户、1 份已发布问卷、3 道题（单选跳转、文本、整数题）、3 份已提交答卷（包含跳过步骤）和 1 份草稿答卷。迁移前单选人数为 2/1、文本有效回答 1 条、数字平均值 34、提交数 3。

| 演练步骤 | 实际结果 |
|---|---|
| 迁移前采集与 dry-run | 三题均可映射；dry-run 报告 `would_link=3, failed=0`，集合计数和数据未变化。 |
| 首次 apply 故障注入 | 在不可变版本插入后、最新版本指针更新前模拟中断；另两题成功关联，失败题明确报告。部分状态为 3 个族/版本、2 个题库条目。 |
| 重复 apply / 恢复 | 修复后的重试把已有版本和条目关联完成，报告 `linked=1, already_linked=2, failed=0`；最新版本指针正确恢复，无重复版本或题库条目。 |
| 迁移后对比 | 原题目 ID、题目字段、题目顺序、跳转规则、发布状态和发布时间不变；只增加来源元数据并更新问卷元数据时间。4 份答卷 BSON 文档完全相同，单问卷统计结果完全相同。 |

演练数据库在完成记录后已删除；没有对真实业务数据库执行 apply。首次定向演练还发现旧版迁移重试会漏修最新版本指针，本轮修复并增加回归测试。第二阶段没有使用跨集合事务；部分步骤中断可能留下未引用的不可变文档，但脚本保留原数据并可重试，不会覆盖或级联删除。执行命令、失败报告及恢复步骤见[迁移说明](migration-question-library.md)。

## 6. 测试、浏览器验收和性能

### 自动化测试

最终全量 pytest 在隔离 MongoDB 上运行，并将 Pydantic 字段警告提升为错误：**64 passed、0 failed、0 skipped in 31.30s**。此前记录的一条 `UnsupportedFieldAttributeWarning` 在当前依赖和完整用例下不能复现；本次没有屏蔽 warning。Python 编译、前端 JavaScript 语法、33 个本地 Markdown 链接、依赖一致性（`pip check`）和 `git diff --check` 均通过；凭据扫描未发现 MongoDB 认证 URI，未发现超过 20 MiB 的文件。各阶段不同基线保留在测试记录中，没有将 skipped 计作通过。

### 浏览器验收

2026-10-27 的双账号真实 Chrome 手工验收记录已保留：实际完成题库、版本历史/恢复、精确版本共享、跨问卷复用与跳转配置、发布、答卷、单问卷与跨问卷统计、撤销授权及发布快照保护。该记录是手动浏览器流程，不是 API 测试。当前项目和虚拟环境没有 Playwright、Selenium 或 Puppeteer 的可重复浏览器测试运行时，本轮未增加新依赖或自动化浏览器套件；多浏览器矩阵和实体移动设备仍未覆盖。

### MongoDB 查询性能

在独立合成数据集（500 份问卷、8,100 份答卷：400 份当前用户问卷、100 份其他用户问卷、8,000 份 submitted、100 份 draft）执行实际查询三次，分别用时 125.68、147.29、125.85 ms，中位数 **125.85 ms**，返回 8,000 条有效回答。explain 的 survey winning plan 使用 `ix_surveys_owner_library_version`，扫描 400 个索引键及 400 个问卷文档；`$lookup` 使用 `ix_responses_survey_status_submitted_at`，`collectionScans=0`、检查 8,000 个索引键/答卷并返回 8,000 行。此为本机 MongoDB 8.3.11 的功能性样本，不是生产容量或并发保证。大规模文本答案会因接口需返回回答列表而增大内存/响应体；极高规模可再考虑分页或异步汇总，但当前不引入可能失配的统计缓存。

自动化、手工浏览器及性能测试的分项步骤和历史测量见[测试用例与结果](test-cases-phase1.md)。

## 7. AI 使用过程与人工决策

AI 在对话中协助审查原始需求、现有架构和工作区代码，生成增量实现、测试与文档草稿；没有把 AI 建议当作默认需求。开发者逐步确定题目共享粒度、旧题逐实例迁移、版本恢复只追加、问卷题目快照优先、撤销不回收已有复用，以及统计只读取当前用户有权访问的数据。本轮还明确要求只修复已确认问题、不操作真实迁移、不提交或推送 Git。

本轮实际修复了迁移部分失败后的 latest-version 指针恢复，并为普通题目版本写入增加一次安全校验/重试，避免写入成功但响应失败导致题库族指针悬空。AI 使用日志保留可核实提示词摘录、实际差异、人工决策和测试输出；早期无法从记录恢复逐字提示的轮次仍标为摘要，不补造原文，见[AI 使用日志](ai-usage-log.md)。

## 8. 局限、待办与总结

八项需求在当前功能边界内均已实现并有对应自动化/API/UI 路径；细分覆盖及测试映射见需求影响分析。实现限制包括：题目版本不可变由服务接口的追加式设计保证，数据库管理员仍能直接修改文档；跨集合操作不依赖 MongoDB 事务，硬故障时可能留下未引用版本或版本号间隙；跨问卷统计只涵盖当前用户有权查看的自有问卷，并严格按精确版本；文本答案数量大时接口返回体会变大。当前性能样本和浏览器检查不代表生产压力、多浏览器或实体设备验收。

部署前由项目负责人/运维在生产副本执行 dry-run、复核失败项、备份并安排迁移窗口；只有明确批准并确认目标数据库隔离后，才执行 `--apply`，再核对 `library_ref`、版本哈希、问卷快照、历史答卷和统计。当前仓库处于 `main` 工作分支且含有既有工作区修改；本轮没有重置、提交或推送任何 Git 变更。
